# 系统架构设计

## 总体分层

```text
客户端（移动 Web / 桌面 Web）
        ↓
API 层（认证、权限、幂等、审计）
        ↓
应用服务（目标、快照、决策、行动、反馈、连接器）
        ↓
确定性内核（资源核算、状态机、版本、规则检查）
        ↘ AI 编排层（抽取、补问、检索、方案解释）
        ↓
PostgreSQL + 对象存储 + 任务队列 + 连接器凭据库
```

## 前端

移动端优先的对话入口用于输入目标、变化和补问；计划页展示当前目标、行动、资源冲突、选择和调整原因；复盘页展示预期与实际。重要状态使用明确标签：待补证、条件建议、建议可供选择；用户选择和执行状态单独显示。

## 后端模块

- `identity`: 用户、会话、时区、授权
- `goals`: 目标、阶段和约束版本
- `snapshot`: 全局快照、领域状态和来源
- `resources`: 时间/资金单位校验与组合核算
- `decision`: S1–S8 状态机、选项和取舍
- `execution`: 行动、依赖、验收和暂停
- `feedback`: 观察窗口、实际结果和复盘
- `connectors`: 日历、任务、文件的授权与增量同步
- `ai-orchestrator`: 结构化抽取、补问、证据绑定和解释
- `trial-analytics`: 试点事件、工时、成本和留存口径
- `audit`: 版本、来源、用户修订和外部动作日志

## 数据流

1. 原始用户输入保存在不可变事件中。
2. 抽取器生成可编辑草稿，用户确认后写入 Goal/Commitment/State。
3. 快照服务生成 revision 和 input fingerprint。
4. 决策服务调用资源内核和 AI 方案生成，输出可复算 Option。
5. 用户选择写入 Decision，不直接覆盖建议。
6. 执行服务创建 Action；连接器事件进入待确认队列。
7. 变化触发新快照和受影响决策重算；旧版本保留历史。
8. 反馈服务在观察窗口后形成 Feedback，并进入下一次决策输入。

## 一致性与安全

资源核算、状态迁移和权限检查必须在服务端确定性执行。AI 不可直接写入外部系统；外部动作必须经过用户明确授权、预览、幂等执行和结果回执。敏感字段加密，凭据使用独立密钥管理；默认不保存不必要的原文。所有读取和外部调用写审计事件。

## 部署建议

早期可采用单体模块化后端 + PostgreSQL + Redis/队列 + 对象存储；AI 与连接器以内部接口隔离，便于替换模型和供应商。先支持单用户/小队列，达到真实留存和成本证据后再拆分服务。必须有本地开发 `.env`、迁移、种子数据和可重复的演示脚本。
