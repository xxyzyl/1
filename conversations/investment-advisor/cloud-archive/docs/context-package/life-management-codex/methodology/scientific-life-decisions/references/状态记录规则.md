# 3.0状态记录规则

重大决定使用人类可读Markdown记录，加一个引用它实际内容的JSON状态记录；小事可直接在回复里完成。JSON不能替代证据、计算和用户授权。没有记录时用户选择与执行状态写“未知”；只有确认未作选择或未开始才填对应状态。执行者必须阅读本规则后填模板，未知保持未知，不能为通过程序而伪造完成状态。

## 字段

| 字段 | 填写规则 |
| --- | --- |
| protocol、decision_id、revision | 3.0、实际记录ID、正整数输入版本；不得保留模板编号 |
| problem | question、goal、source写用户问题、目标及可定位会话/材料；constraints仅放硬约束，每项为id、description、source。未明确不等于没有约束，把影响选择的未知写入gaps |
| evidence | 每项id、source、date、checked_at、status、decisive；status仅为用户陈述/已核实/假设/待核实，decisive是是否影响当前建议。日期未知可写未知，不能把用户陈述标成外部核实 |
| options | 每项id、description、constraint_checks；后者逐项覆盖全部硬约束ID，值为满足/不满足/未知。支持检查的材料和计算在description引用或主记录对应表中定位 |
| gaps | 每项description、stage、severity、resolved；stage是需返回的S1—S5，severity为阻断/条件，resolved为布尔值；已解决还要resolution。此处只记影响建议的缺口，权限与执行另外记录 |
| comparison | 当前revision、input_fingerprint、method、artifact、全部备选option_ids、实际依据evidence_ids、strongest_objection、reversal_conditions、conditions；artifact为具体结果或主记录中可定位的产物，不是“已分析”三个字。仅一个方案还需single_option_reason |
| review | 当前revision、input_fingerprint、target_fingerprint、completed、mode、artifact；mode为主智能体自审/子智能体复核/外部专业复核。子智能体模式须有真实task_id；真实查了什么、未查什么在artifact说明 |
| recommendation | status为待补证/条件建议/建议可供选择，option_ids为实际推荐的备选ID；没有实际推荐可为空并保持待补证 |
| user_choice | status为未知/未决定/已决定/暂缓；已决定才填option_ids，并附用户真实选择的source、选择当时的revision与selection_fingerprint |
| execution | status为未知/未开始/执行中/已暂停/已完成/已停止；开始过实际工作就填authorization_source与action_record。授权可来自当前或之前会话的明确要求，不要求用户重复确认；此字段本身不创造权限 |

证据重要性、约束满足和缺口分级由主协调者根据实际材料判断，脚本不会替其进行语义核实。仅引用背景资料不能支撑决定性结论；所有决定性主张都须进入比较的证据对应。

## 检查与输入变化

1. 填好问题、证据、方案和缺口，在实际分析开始时取得输入指纹：`python3 <技能目录>/scripts/decision_engine.py <状态记录.json> --fingerprint`。
2. 做完比较后填写其版本与input_fingerprint。确定建议对象，运行同一脚本加 `--review-fingerprint` 得到复核对象指纹；真实复核完成后填review的版本、input_fingerprint及target_fingerprint，并保留产物。取得指纹不能代替分析完成。
3. 用户已实际选择后，用 `--selection-fingerprint` 获取当时目标、硬约束及已选方案的内容指纹，写入user_choice；取得指纹不创造选择或授权。方案内容变化导致不匹配时核对旧选择与授权的适用范围，不能只复用旧方案ID。
4. 运行 `python3 <技能目录>/scripts/decision_engine.py <状态记录.json>`，读取supported_recommendation_status、blocking_issues、record_issues、execution_issues和next_stage。不能只看退出码。
5. 退出0表示记录没有发现格式或显式状态夸大，不表示建议已通过；一个诚实的待补证记录也会返回0。退出1表示状态/执行声明冲突；退出2表示格式错误。
6. 目标、证据、约束、方案或缺口变化会改变输入指纹；比较正文或建议对象变化也会使复核对象指纹失效；实质变化还要递增revision。核对受影响部分再更新分析与复核，不可只复制新指纹来“刷新通过”。程序无法判断作者是否真的重新分析，仍须查看实际产物。

已知违反或尚未核实的硬约束会阻止对该方案给出可执行推荐。若只能在放宽条件后成立，把放宽内容作为明确的新问题/情景记录，未经用户认可不写成原约束已经变更。可行的补证或试行动作可以作为独立方案，但不能借此掩盖主要选择仍未解决。

建议状态是脚本所读取记录能支持的上限，主协调者可以更保守；不得高于该上限。缺失或格式化捏造的实际事实可能逃过脚本，必须保留人工/模型语义核查。

## 与Markdown对应

新Markdown记录标记协议3.0，记录编号、输入版本、建议状态、用户选择、执行状态与JSON保持一致。用 `python3 <技能目录>/scripts/check_decision.py <记录.md> --state <状态记录.json>` 联合检查。旧2.0记录无需迁移，按原有结构读取；用户请求更新旧决定时另建新版，不能抹去当时信息。
