# SPEC.md — 人生管理系统 4.0 需求说明

## 1. 项目目标

人生管理系统 4.0 要做成一个可长期使用的 AI 个人决策与行动协调产品。它帮助用户把人生中的目标、承诺、资源、行动和反馈放在同一个系统里检查，尤其处理“单个计划看起来合理，但合在一起做不到”的问题。

系统不替用户决定人生价值，不把收入、健康、关系、自由时间压成一个总分。用户给出价值方向、阶段目标和底线，系统负责澄清问题、整理证据、生成备选、检查资源冲突、协助执行，并在条件变化后提醒复核。

## 2. 产品定位

首个商业化场景建议聚焦在“在职职业转型与长期能力成长”。目标用户是已有工作或生活承诺，同时需要推进学习、作品、接单、求职、财务安全和恢复的人。

MVP 要验证的不是大而全的人生操作系统，而是一个闭环：用户提出目标，系统识别现实约束，形成可执行计划，跟踪执行证据，在新信息出现时调整建议。

## 3. 核心角色

| 角色 | 权限与责任 |
|---|---|
| 用户 | 决定价值、目标、底线和是否执行；可修改、删除、撤销授权 |
| 人生总控 | 维护全局状态，协调九个人生领域，调用八阶段决策引擎 |
| 人生领域模块 | 描述生活中不同方面的状态、约束、机会和风险 |
| 共享能力模块 | 提供逻辑、统计、资源配置、心理、系统控制、法律、健康等分析方法 |
| 执行与记录服务 | 保存决策、行动、反馈、授权、来源和版本 |

## 4. 功能模块

### 4.1 全局档案与目标模块

保存用户主动提供或授权导入的信息，包括价值方向、阶段目标、底线、时间预算、财务边界、已有承诺、偏好、禁用事项和默认沟通方式。

任何来源的信息都必须带来源、时间和可信度。系统不能把“缺少数据”当作“不存在问题”，也不能把一次临时偏好当作永久规则。

### 4.2 九个人生领域模块

| 编号 | 领域 | 主要内容 |
|---|---|---|
| D01 | 身体健康与恢复 | 睡眠、体能、疾病照护、恢复需求、医疗相关事实 |
| D02 | 心理状态与自我调节 | 情绪、压力、注意力、自我调节、心理安全边界 |
| D03 | 关系、家庭与照护 | 家庭、朋友、亲密关系、承诺、照护责任 |
| D04 | 职业、劳动与价值创造 | 工作、创业、接单、交付、收入来源 |
| D05 | 学习、能力与探索 | 课程、练习、作品、能力证据、迁移能力 |
| D06 | 财务、资产与保障 | 收支、现金流、风险承受、保险、债务、储蓄 |
| D07 | 居住、日常与基础设施 | 居住、交通、家务、证照、工具、数字基础设施 |
| D08 | 社群、公共参与与生态责任 | 社群参与、公共责任、社会关系中的义务 |
| D09 | 休闲、审美与生命体验 | 休息、玩乐、艺术、审美、旅行、生命体验 |

### 4.3 二十三个共享能力模块

二十三个能力模块来自现行 `scientific-life-decisions` Skill。它们不是常驻服务，也不是必须每次全部调用，而是按问题调用的方法库。模块清单见 [docs/MODULE_CATALOG.md](docs/MODULE_CATALOG.md)。

### 4.4 八阶段决策引擎

| 阶段 | 名称 | 产物 |
|---|---|---|
| S1 | 定义问题 | 决策对象、范围、成功标准、不可越过的底线 |
| S2 | 收集证据 | 已知事实、未知事实、来源、需要补证的问题 |
| S3 | 生成备选 | 至少一个可执行方案和可比较的替代方案 |
| S4 | 约束与比较 | 先检查硬约束，再比较收益、代价、风险和机会成本 |
| S5 | 反方复核 | 找出最强反例、遗漏条件、过度自信和伦理风险 |
| S6 | 建议与选择 | 系统建议、用户选择、暂缓或继续补证 |
| S7 | 授权执行 | 仅在已授权范围内转为行动、日程、任务或外部操作 |
| S8 | 反馈更新 | 记录实际结果、延迟效果、条件变化和后续复核 |

### 4.5 资源核算模块

资源核算要检查时间、金钱、精力、注意力、承诺、恢复、设备等资源。默认公式为：

`baseline_existing_commitments + unique_action_demands + reserve <= capacity`

规则：

- 同一个行动同时服务多个领域时，只计算一次实际投入。
- 互斥方案不能相加；同一方案内的共同行动要去重。
- `null` 表示未知，不能当作 0；0 表示明确没有消耗。
- 金额、时间、周期、单位必须一致。
- 资源冲突是状态，不等于脚本失败；API 要把冲突返回给前端显示。

### 4.6 状态与版本模块

系统必须分别保存建议、用户选择和执行状态。

| 维度 | 允许值 |
|---|---|
| recommendation_status | `needs_evidence`、`conditional`、`ready_for_choice` |
| choice_status | `unknown`、`undecided`、`decided`、`deferred` |
| execution_status | `unknown`、`not_started`、`in_progress`、`paused`、`completed`、`stopped` |

条件变化时，不覆盖用户过去的选择，而是把相关评估标为 `stale`，要求重新比较。触发复核的变化包括目标变化、硬约束变化、方案变化、资源预算变化、授权撤销、关键事实被纠正、外部结果与预期不符。

### 4.7 主动服务模块

主动服务只能在用户明确授权的数据源、目标和提醒范围内运行。第一版只做“可解释的候选建议”：发现冲突或机会后生成草稿，等待用户确认。任何外部发送、下单、报名、付款、联系他人等动作都需要明确授权和可撤销记录。

## 5. 用户流程

### 5.1 初次设置

1. 用户说明当前最重要的阶段目标。
2. 系统询问必要的时间、财务、已有承诺和底线。
3. 系统建立第一版全局快照，标记未知项。
4. 用户确认哪些数据可以保存，哪些只能用于本次对话。

### 5.2 单次重大决策

1. 用户提出问题，例如“是否接一个副业项目”。
2. 总控判断涉及 D04 职业、D05 学习、D06 财务、D03 家庭和 D01 恢复。
3. 系统运行 S1-S5，生成方案和冲突说明。
4. 用户选择执行、暂缓或补证。
5. 如果选择执行，系统生成行动清单和复核时间。
6. 后续根据结果更新状态。

### 5.3 周复盘

1. 汇总本周执行、未完成、异常和新信息。
2. 检查全局资源是否超载。
3. 把可以保持的计划延续，把失效计划转入复核。
4. 只保留少量下一步行动，避免复盘本身变成负担。

### 5.4 职业转型 MVP 流程

1. 记录目标岗位、现有能力、可用时间、现金流安全边界。
2. 生成学习、作品、投递或接单方案。
3. 每周检查作品证据和真实时间消耗。
4. 根据反馈调整学习比例、作品范围或求职节奏。

## 6. 数据结构设想

详细结构见 [docs/DATA_MODEL.md](docs/DATA_MODEL.md)。最小核心实体包括：

| 实体 | 说明 |
|---|---|
| user_profile | 用户基础设置、时区、偏好、授权摘要 |
| life_snapshot | 某一时点的目标、领域状态、资源预算和承诺 |
| goal | 阶段目标、优先级、状态、适用时间 |
| constraint | 硬约束、软约束、来源和有效期 |
| decision_case | 一次决策的问题、阶段、状态和版本 |
| option | 备选方案、行动、收益、代价、风险 |
| resource_ledger | 容量、基线、储备、行动消耗和核算结果 |
| evidence_item | 事实、来源、采集时间、可信度、纠正历史 |
| action_item | 下一步行动、负责人、截止时间、执行状态 |
| feedback_event | 实际结果、观察值、延迟效果、解释与后续复核 |
| authorization | 用户授权范围、数据源、操作类型、撤销状态 |
| audit_event | 重要读写、建议生成、执行请求和用户确认记录 |

## 7. 接口设想

详细接口见 [docs/API_CONTRACT.md](docs/API_CONTRACT.md)。MVP API 可以从以下端点开始：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/intake/messages` | 接收用户输入，抽取候选事实和决策问题 |
| GET | `/api/v1/life/snapshot` | 返回当前全局快照 |
| POST | `/api/v1/decision-cases` | 创建一次决策 |
| POST | `/api/v1/decision-cases/{id}/run` | 运行或继续八阶段决策 |
| POST | `/api/v1/resource-checks` | 对方案进行资源核算 |
| POST | `/api/v1/choices` | 保存用户选择 |
| POST | `/api/v1/actions` | 创建授权范围内的行动 |
| PATCH | `/api/v1/actions/{id}` | 更新执行状态 |
| POST | `/api/v1/feedback-events` | 保存实际结果和观察 |
| GET | `/api/v1/review-queue` | 查看需要复核的旧建议 |
| POST | `/api/v1/authorizations` | 创建或更新授权 |
| DELETE | `/api/v1/authorizations/{id}` | 撤销授权 |

## 8. 非功能需求

- 本地开发默认使用 mock 模型和手工数据，不需要真实外部账号。
- 数据写入必须可追溯来源和时间。
- 重要行动必须幂等，避免重复发送或重复创建任务。
- 用户撤销授权后，队列中尚未执行的外部动作必须停止。
- 后端必须以服务端权限为准，前端不能决定授权是否有效。
- API 返回结构稳定，便于日后替换模型供应商。
- 测试先覆盖决策状态、资源核算、授权边界和版本失效。

## 9. MVP 完成标准

MVP 不要求连接日历、邮箱或支付系统。完成标准是：

- 用户能创建一个职业转型目标和一组现实约束。
- 系统能生成至少两个可比较方案。
- 系统能发现时间或预算冲突，并解释冲突来源。
- 用户能保存选择和下一步行动。
- 新事实进入后，相关旧建议会被标为需要复核。
- 所有行为有来源、版本和审计记录。
