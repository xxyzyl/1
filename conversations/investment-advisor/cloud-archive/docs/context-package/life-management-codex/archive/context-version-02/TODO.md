# 下一步开发任务

## P0：先做出可运行的本地最小闭环

- [ ] 建立统一项目目录和 Python/TypeScript 基础工程，保留现有 Markdown 数据。
- [ ] 定义领域、目标、行动、观察、决策、建议、反馈的 JSON Schema 或数据库模型。
- [ ] 实现 Markdown/JSON 导入导出与幂等去重。
- [ ] 把现有八阶段协议封装为可调用的决策流水线，输出结构化决策记录。
- [ ] 实现共同时间、资金、精力和承诺的冲突检查。
- [ ] 实现主动补问队列：只生成会改变建议的问题，支持跳过、回答和过期。
- [ ] 为现有规则补齐自动化测试，覆盖数据缺失、同步失败、资源去重、反馈延迟和用户纠正。

## P1：接入数据并减少手工操作

- [ ] 先支持本地指定目录文件、CSV/JSON、日历和待办的只读导入。
- [ ] 建立 Source/Consent/SyncRun/AuditEvent 模型和同步日志。
- [ ] 实现变化同步、来源关联、重复记录合并和用户确认队列。
- [ ] 建立通知抽象，支持终端提示和邮件/日历提醒草稿，但默认不外发。
- [ ] 建立总控快照、周复盘和建议反馈页面或命令行界面。

## P2：产品化基础

- [ ] 加入账户、会话、权限和多设备同步；敏感领域单独授权。
- [ ] 建立加密存储、密钥管理、备份恢复、导出删除和隐私审计。
- [ ] 建立领域插件接口和数据源适配器。
- [ ] 建立建议质量指标：数据新鲜度、重复提问率、用户修正率、建议采纳率、行动完成率和复盘有效性。
- [ ] 以匿名或合成数据完成两周可用性试验，验证是否真的减少用户操作。

## P3：商业化验证

- [ ] 明确第一目标人群和一个高频痛点，不同时解决所有人生领域。
- [ ] 制作可演示原型，展示“输入变化→主动追问→跨领域冲突→建议→反馈”的完整链路。
- [ ] 访谈潜在用户，验证付费意愿、隐私顾虑和可接受的自动化边界。
- [ ] 设计个人版、专业顾问版或机构版的服务边界与合规方案。
