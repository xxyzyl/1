# AGENTS.md

## 工作目标

你正在开发“人生管理系统 4.0”。先实现可验证的最小闭环，再扩展复杂功能。任何实现都必须服务于：目标澄清 → 事实与证据 → 方案 → 约束比较 → 复核 → 选择 → 执行 → 反馈。

## 开发原则

1. 先读 `README.md`、`SPEC.md`、`ARCHITECTURE.md`、`TODO.md`，再修改代码。
2. 事实、用户陈述、机制假设和未知必须分开存储和展示。
3. 缺失值不得自动当作 0；未知必须显式标记。
4. 硬约束优先于评分、推荐或优化结果。
5. 共同时间、资金和承诺不得重复计入；共享任务可以产生多个价值，但实际资源只计一次。
6. 分开记录 `recommendation`、`user_decision`、`execution_status`；没有执行证据时为 `unknown`，不得写成“未开始”。
7. 目标、关键证据、方案或资源改变时，旧比较和复核必须失效或重新验证。
8. 精力和情绪是状态/边界，不得未经用户同意折算成金钱分数。
9. 数据应遵循最小必要原则；敏感信息默认不采集、不外传。
10. AI 输出必须可追溯到输入、来源、时间和不确定性；不得伪造概率、来源、执行结果或用户偏好。

## 代码风格

- 默认使用 TypeScript，严格类型检查，优先小模块、纯函数和明确的数据结构。
- API 输入输出使用版本化 schema；所有时间使用 ISO 8601 和明确时区。
- 枚举值使用稳定英文标识，界面可显示中文；数据库字段避免含糊缩写。
- 领域逻辑与外部服务、模型调用、数据库访问分离。
- 函数只做一件事；复杂规则写成可测试的 policy/validator，而不是散落在 UI 中。
- 注释解释“为什么”，不重复“做了什么”；重要设计决策写入 ADR。
- 测试优先覆盖硬约束、未知值、重复资源、过期复核、状态不一致和回退路径。

## Git 与交付

- 每次改动保持小而可回滚，提交信息说明行为变化。
- 新功能必须同时补 schema、测试和必要文档。
- 不要把真实密钥、个人敏感数据或生产数据提交到仓库。
- 运行 lint、类型检查和测试后再交付，并报告未运行或失败的检查。

## 禁止事项

- 不得把系统描述成已经接入日历、任务、银行、健康或其他平台。
- 不得把 PPT、流程图或示例案例当作已部署产品。
- 不得自动替用户作出不可逆决定、发送消息、花钱、修改重要记录或执行外部操作。
- 不得用高分掩盖硬约束冲突。
- 不得把相关关系写成因果关系，不得把假设写成事实。
- 不得默认用户已选择方案或已执行行动。
- 不得为了“完整”要求用户一次填完 9 个领域。
- 不得在缺少授权、数据新鲜度不足或关键冲突未确认时给出确定性结论。
