# Codex 开发规则

## 总原则

你正在开发“人生管理系统”，不是普通待办事项应用。每次改动都必须说明它服务于哪个业务规则、改变了哪个状态或数据流，以及如何验证。

优先实现小而可验证的纵向切片：输入目标和约束，形成决策记录，检查硬约束与共享资源，输出下一步行动和可追踪反馈。不要因为架构图中存在 9 个领域和 23 个能力模块，就一次性实现 32 个常驻代理。

## 开发顺序

1. 先阅读根目录文档和 `docs/CONTEXT.md`。
2. 先建领域模型、状态机、版本和审计记录，再建 UI 和连接器。
3. 规则判断优先使用确定性代码；模型只负责抽取、归纳、候选生成和解释，不能绕过硬约束。
4. 每项功能先写失败测试，再实现，再运行全量测试。
5. 外部连接器必须可关闭、可重试、可撤销；没有权限或没有证据时返回未知，不猜测。

## 代码风格

- 使用清晰、短小、单一职责的模块；业务规则命名应接近领域语言。
- API 输入输出使用显式 schema；时间统一使用带时区的 ISO 8601，金额必须带币种，时长必须带单位。
- 数据库记录不可通过无版本覆盖方式更新；重要对象使用 append-only 事件或版本快照。
- 错误分为输入错误、权限错误、外部服务错误、规则冲突和未知状态；不要把未知转换为 false、0 或“未开始”。
- 日志不得写入秘密、完整敏感内容或不必要的个人数据；日志应带 request/event id。
- 注释解释业务原因和边界，不重复代码表面含义。

## 决策引擎规则

- 每个决策必须能定位到 S1-S8 当前阶段和产物。
- `recommendation_status`、`choice_status`、`execution_status` 三者分开存储。
- `execution_status` 无记录时只能是 `unknown`，展示层中文为“执行情况未知”。
- 目标、证据、方案、资源、约束任一版本变化，都要使受影响的比较/复核标记为 stale。
- 方案先过硬约束，再比较收益、成本、风险、机会成本、可逆性和延迟。
- 复核必须留下反对理由、关键假设、反转条件和待处理问题。
- 用户的价值选择不能由统计模型自动推导；其他人不能被建模为无条件可控制资源。

## 测试要求

至少覆盖：高分但违反硬约束；无执行记录；证据变化后旧复核失效；方案变化后旧选择失效；共享任务去重；重复记账；时间/预算不足；外部连接器失败与重试；用户撤销授权；自动观察与用户确认结果不一致；延迟反馈尚未到期；目标已暂停。

## 禁止事项

- 禁止把建议写成决定，把决定写成执行，把执行写成完成。
- 禁止默认空值为零、未提供为否、没有日志为未开始。
- 禁止用综合评分抵消硬约束。
- 禁止未经明确授权读取通讯录、定位、电脑操作、健康、财务或第三方账户数据。
- 禁止自动发送消息、交易、预约、删除或修改外部数据，除非动作、范围和授权明确且可审计。
- 禁止伪造来源、概率、用户结果、测试结果或“已经部署”的说法。
- 禁止将模型输出直接作为事实、医疗/法律/投资结论或人格判断。
- 禁止删除用户已有文件、记录或迁移数据而不提供可恢复方案和明确说明。
